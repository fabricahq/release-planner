The first release of Release Planner: tell your coding agent "let's release," review the notes it drafts in a pull request, and merge to publish. Release Planner gathers every change since your last release, and your agent writes the notes following your release policy and style.

Install it:

```sh
curl -fsSL https://raw.githubusercontent.com/fabricahq/release-planner/v0.1.0/install.sh | sh -s -- --version v0.1.0
```

## ✨ New Features

### Releases approved by merging a pull request

Your agent opens a pull request that adds `releases/<version>.md`. You edit it like any other file, and merging it publishes the release. The generated Release workflow checks the request, runs any release checks you configured, tags the merged commit, and publishes the notes word for word. Nothing is tagged before you merge, and a direct push of notes publishes nothing. (#1)

### Commands for agents: `guide`, `inventory`, `draft`, and `plan`

- `guide` prints the complete release procedure for your pinned version, including your release notes style.
- `inventory` lists the previous release, every commit since it with its pull request, and the candidate next versions.
- `draft <version>` creates the notes file with a **What's Changed** list and a closing changelog link.
- `plan` checks a release request before you merge it: one notes file, a version newer than every tag, immutable published notes, and no leftover draft placeholder or empty headings.

(#1)

### Generated files that can't drift

`release-planner init` creates `.release-planner/config.yml` and a starter release policy. `release-planner install` generates the Release workflow, a `release` skill for agents in `.agents/skills/` and `.claude/skills/`, and a marked **Releases** section in `AGENTS.md`. Running `install` again changes nothing unless your config changed, it never touches your own text in `AGENTS.md`, and it refuses to overwrite hand edits. `release-planner check` runs on every release pull request, so a stale or edited file fails before it can cause a bad release. (#1)

### Your release policy and notes style

- **Release policy:** `.release-planner/policy.md` says what counts as a breaking change, how to choose a version (including before 1.0.0), who reads your notes, and the order changes appear in. The agent stops and asks while any `TODO:` line remains.
- **Release notes style:** by default, notes open with what the release means for readers and use ✨ New Features, ⬆️ Improvements, 🐛 Squashed Bugs, and ⛓️‍💥 Breaking Changes, with pull request numbers on every entry. Name your own style file in `config.yml` to add to the default or replace it.

(#1)

### Optional release checks

Run a script, with Go, Node, or Python set up, or call one of your own workflows on the exact commit being released, before it's tagged. Your checks never receive the token that can write releases. (#1)

### Verified binaries

Each release includes archives for macOS and Linux on amd64 and arm64, with a `SHA256SUMS` file and a signed build attestation. `install.sh` checks the checksum before installing, and the generated workflow also verifies the attestation. (#1)
