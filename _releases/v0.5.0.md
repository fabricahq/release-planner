## ✨ New Features

### Run GitHub Actions workflows before a release is published

Some releases need a change outside the repository before anyone can use them, such as running a database migration. You can now list your own GitHub Actions workflows under `pre-publish`, and Release Planner runs them after you merge the release pull request and before it tags the release. If one fails, nothing is tagged or published:

```yaml
pre-publish:
  - workflow: migrate-database.yml
```

See [pre-publish workflows](https://release-planner.fabricahq.com/customize/pre-publish/). (#32)

### Run GitHub Actions workflows after a release is published

We've renamed `downstream` to `post-publish` for consistency with the `pre-publish` option. It's not new functionality, but you can list workflows under `post-publish` to run them after a release publishes. They can be in this repository, such as one that deploys the release, or in another repository you own, such as one that updates a Homebrew tap:

```yaml
post-publish:
  - workflow: deploy.yml
  - repository: your-org/homebrew-tap
    workflow: update-formula.yml
```

See [post-publish workflows](https://release-planner.fabricahq.com/customize/post-publish/). (#32)

### Publish with your own GitHub App

You can now have Release Planner publish with a dedicated GitHub App whose key only the `release` environment holds. The App can tag a release commit whose workflow files have changed since, which the workflow's own token can't, and it lets a tag ruleset reserve release tags for Release Planner. Add `RELEASE_APP_CLIENT_ID` and `RELEASE_APP_PRIVATE_KEY` to the `release` environment to turn it on. See [Publish with a release GitHub App](https://release-planner.fabricahq.com/start-here/set-up/#publish-with-a-release-github-app). (#32)

## 🐛 Squashed Bugs

### A withdrawn release stays withdrawn

Deleting an untagged release's notes file withdraws it, and editing the file requests that version again. Retrying the original release run afterwards still published the withdrawn release or its old release commit, and retrying an old notes edit restored the older notes over a newer one. The release workflow now refuses to publish a request that a later change on the release branch withdrew or replaced, and checks again immediately before each write. To replace a broken release, delete its notes file in the pull request that fixes the cause, then release again; see [If publishing fails](https://release-planner.fabricahq.com/start-here/release/#if-publishing-fails). (#32)

### Releases merged close together all publish

When three releases waited to publish at the same time, the newest one cancelled the one in the middle, which then needed a manual re-run. Waiting releases now publish one at a time, in the order their runs started. (#32)

### The release status names every failed job

When several jobs failed, the summary at the top of the release pull request's description and the comment that mentions whoever merged named only the first one, by its job name. They now name every job that failed or was cancelled, as the jobs table names it, such as **Deploy**. Each row in the jobs table links the job from the latest attempt that ran it, so after **Re-run failed jobs** it opens the result that counts, and a failed workflow's row opens its failing job. (#35)

## ⛓️‍💥 Breaking Changes

### `downstream` is now `post-publish`

If your config lists `downstream` workflows, `release-planner install`, `check`, and the Release workflow refuse the config once you pin v0.5.0, until you move them under `post-publish`. The entries stay the same, and they still skip prereleases. The jobs that start them now run in an environment named `dispatch`, which holds the GitHub App's credentials as `DISPATCH_APP_CLIENT_ID` and `DISPATCH_APP_PRIVATE_KEY`. The same GitHub App works. GitHub can't rename an environment, so you create `dispatch` and delete `downstream` afterwards. (#32)

For tool authors: the `release-planner downstream` command is now `release-planner dispatch`, and `report --downstream` is now `report --hooks`. Only the generated Release workflow uses them, and `install` updates it.

### The release assets workflow must output its artifact's ID

If you use `release-assets`, the Release workflow now downloads your files by the ID of the upload your workflow made, instead of by name, so no other job in the run can replace them by uploading under the same name. `release-planner install` and `check` fail until your workflow outputs that ID as `artifact-id`. These are the parts to add; [release assets](https://release-planner.fabricahq.com/customize/release-assets/) has the full example:

```yaml
on:
  workflow_call:
    outputs:
      artifact-id:
        value: ${{ jobs.build.outputs.artifact-id }}
jobs:
  build:
    outputs:
      artifact-id: ${{ steps.upload.outputs.artifact-id }}
    steps:
      - id: upload
        uses: actions/upload-artifact@v7
        with:
          name: release-assets
          path: dist/
```

(#32)

### Upgrade steps

1. Install v0.5.0:

   ```sh
   curl -fsSL https://raw.githubusercontent.com/fabricahq/release-planner/v0.5.0/install.sh | sh -s -- --version v0.5.0
   ```

2. Set `version: v0.5.0` in `.release-planner/config.yml`.
3. If your config has `downstream:`, rename it to `post-publish:` and keep its entries as they are.
4. If you renamed `downstream:`, open **Settings → Environments**, create an environment named `dispatch`, and give it the same deployment branch rule as your `downstream` environment. Add the variable `DISPATCH_APP_CLIENT_ID`, set to the GitHub App's Client ID, and the secret `DISPATCH_APP_PRIVATE_KEY`, set to its private key. These are the values of `DOWNSTREAM_APP_CLIENT_ID` and `DOWNSTREAM_APP_PRIVATE_KEY`. GitHub doesn't show a secret's value, so if you no longer have the private key, generate a new one in the App's settings. See [Set up the dispatch environment](https://release-planner.fabricahq.com/customize/post-publish/#set-up-the-dispatch-environment).
5. If you use `release-assets`, give your workflow's upload step an `id`, output its `artifact-id` from the job, and declare an `artifact-id` output under `workflow_call`, as shown above. See [Upgrade to v0.5.0](https://release-planner.fabricahq.com/customize/release-assets/#upgrade-to-v050).
6. Run `release-planner install`, and commit everything in one pull request.
7. Once a release has run its post-publish workflows, delete the `downstream` environment.
