## ✨ New Features

### Release notes are checked before you merge

`release-planner validate` now checks your release notes against a set of rules. Your agent can't hand you notes with an empty or duplicated section, a heading that runs on for a paragraph, a missing Full Changelog link, or a pull request left out of the list. When your agent runs `validate`, a broken rule fails, so the agent fixes the notes before opening the pull request. In the Release workflow, a broken rule is only a warning. It never blocks the merge or the release, so you can break a rule on purpose when you edit the notes. (#13)

There are six rules. `release-planner validate --rules` lists them, and you can turn one off in `.release-planner/config.yml`:

```yaml
release-notes-rules:
  no-long-heading: off
```

See [release notes rules](https://release-planner.fabricahq.com/customize/release-notes-style/#release-notes-rules) for what each one checks.

## ⬆️ Improvements

### Notes written in one pass, with every change listed

Your agent now writes the whole notes file at once instead of splicing text around a generated draft, which is how stale copies of earlier drafts ended up in the notes. `release-planner inventory` gives it a ready-made line for every pull request, direct commit, and new contributor, plus the closing link, and the agent groups those lines by reading each pull request rather than trusting its title's prefix. When revising, it edits the notes in place and never regenerates them, so your edits survive. (#13)

### Also in this release

- When your release pull request merges `main` in to pick up newer changes, the list of changes stays the same before and after the merge, and adding the new pull requests is all that's left to do. (#13)
- The list of changes leaves out the release request itself and empty commits, and counts a merge titled like `Fix login (#7)` as that pull request. (#13)
- The notes start at the first heading unless your release notes style asks for an opening. (#13)
- For tool authors: `inventory` adds `entry` lines and a `closing` line to its JSON, and works without an `origin` remote. `validate` takes `--repository owner/name`, for a fork's clone. (#13)

## ⛓️‍💥 Breaking Changes

### Three config keys are renamed

These keys in `.release-planner/config.yml` are renamed so each says what it's for. Release Planner rejects the old names, so until you rename them, `install`, `inventory`, `validate`, and the Release workflow fail with an unknown-field error. (#13)

| Before | After |
| --- | --- |
| `validate:` | `release-checks:` |
| `notes-dir:` | `release-notes-dir:` |
| `branch:` | `release-branch:` |

### `plan` is now `validate`, and `draft` is gone

`release-planner plan` is renamed `validate`, with the same flags and output, and `release-planner draft` is removed; your agent writes the notes from `inventory` instead. The Release workflow's jobs are renamed to match: `plan` becomes `validate`, and `validate` becomes `release-checks`. If a script calls `plan` or `draft`, or a branch ruleset requires a check named `plan` or `validate`, update it, or the script fails and the ruleset waits for a check that never runs. (#13)

### Upgrade steps

1. Install v0.3.0:

   ```sh
   curl -fsSL https://raw.githubusercontent.com/fabricahq/release-planner/v0.3.0/install.sh | sh -s -- --version v0.3.0
   ```

2. Set `version: v0.3.0` in `.release-planner/config.yml`, and rename any of `validate:`, `notes-dir:`, and `branch:` it uses to `release-checks:`, `release-notes-dir:`, and `release-branch:`.
3. Replace `plan` with `validate` in any script that runs Release Planner, and remove any use of `draft`.
4. If a branch ruleset or branch protection rule requires one of the Release workflow's checks, update its name: `plan` is now `validate`, and `validate` is now `release-checks`.
5. Run `release-planner install` to update your Release workflow, agent guide, and release skill, then commit everything in one pull request.
