Release Planner v0.2.0 does more of the release notes' raw material for your agent: every pull request with its author, and new contributors. It also warns when the `release` environment isn't set up as recommended. One breaking change: release notes now default to `_releases/`, so repositories that keep them in `releases/` need one line of config or a move. The upgrade steps are under Breaking Changes.

## ✨ New Features

### Pull requests and new contributors in every draft

`release-planner draft` now lists every pull request merged since the last release as `- <title> by @<handle> in #<number>`, with direct commits linked by SHA, under `## Pull Requests`, which replaces `## What's Changed`. When a release includes someone's first contribution, it adds `## New Contributors`. Handles come from GitHub, never from git author names, and anything `draft` can't look up is printed as a warning. The default style groups the list by conventional-commit type. (#6)

`release-planner inventory` also reports each commit's `authorHandle`, the release's `newContributors`, and `warnings` in its JSON output. (#6)

### A warning when the release environment isn't set up

`plan` now checks the repository's `release` environment and warns, without failing, when it's missing, lets any branch publish, would block publishing from your release branch, or requires reviewers that would hold every release for a second approval. The warnings appear as annotations and in the run summary, with a link to the [setup steps](https://release-planner.fabricahq.com/start-here/set-up/#create-the-release-environment). The generated workflow gives the plan job `actions: read` so it can read those settings. (#7)

### Move published notes to a new directory

Changing `notes-dir` no longer strands published notes. `plan` accepts a notes file added for an already-published tag when it's byte for byte the notes that tag published, and treats it as history instead of a new release. Notes changed along the way are still refused. (#10)

## ⬆️ Improvements

- The documentation is live at [release-planner.fabricahq.com](https://release-planner.fabricahq.com). (#8)
- [Set up a repository](https://release-planner.fabricahq.com/start-here/set-up/#create-the-release-environment) explains how to create the `release` environment: limited to your release branch, without required reviewers, because merging the release pull request is the approval. (#5)
- The config `init` writes says which GitHub Actions workflow a `version` bump upgrades: `.github/workflows/release-planner.yml`. (#9)

## ⛓️‍💥 Breaking Changes

### Release notes default to `_releases/`

When `.release-planner/config.yml` doesn't set `notes-dir`, notes now live in `_releases/` instead of `releases/`. The underscore keeps them apart from your repository's own content. A repository that relies on the old default would otherwise stop seeing its release requests. (#10)

### Custom styles that mention What's Changed

`draft` now writes `## Pull Requests` instead of `## What's Changed`, and the agent guide tells agents to keep it. If your release notes style or policy refers to What's Changed, rename it so the two agree. (#6)

### Upgrade steps

1. Install v0.2.0:

   ```sh
   curl -fsSL https://raw.githubusercontent.com/fabricahq/release-planner/v0.2.0/install.sh | sh -s -- --version v0.2.0
   ```

2. Set `version: v0.2.0` in `.release-planner/config.yml`.
3. If your notes are in `releases/` and the config doesn't set `notes-dir`, choose one:
   - Keep them there: add `notes-dir: releases`.
   - Move them: `git mv releases _releases`. `plan` accepts published notes moved unchanged.
4. If your release notes style or policy mentions What's Changed, change it to Pull Requests.
5. Run `release-planner install` to regenerate the workflow, the agent guide, and the release skill, then commit everything in one pull request.
