## ✨ New Features

### Attach files to your releases

Release Planner can now publish binaries, archives, and any other files with your release. Point `release-assets` at a workflow in your repository that builds them:

```yaml
release-assets:
  workflow: build-release.yml
```

The files are built and signed with build provenance as soon as the release pull request opens, so a broken build shows up before you approve anything. Merging publishes those exact files, without rebuilding them. See [release assets](https://release-planner.fabricahq.com/customize/release-assets/). (#22)

### See the release's progress on the pull request

The release pull request's description now shows the release as it happens: what merging will do, the version, each job with a link to it, rule findings, and the built files with download links. After the merge, it links the published release. If anything fails after the merge, a comment mentions whoever merged, so a failed release doesn't go unnoticed. (#22)

### Start other workflows after a release

List workflows in other repositories, such as a Homebrew tap, and Release Planner starts each one after a new stable release, passing the tag and version. A failed downstream workflow never affects the release itself. See [downstream workflows](https://release-planner.fabricahq.com/customize/downstream/). (#22)

```yaml
downstream:
  - repository: fabricahq/homebrew-tap
    workflow: update-code-rules.yml
```

### Fix release notes after publishing

To correct a published release's notes, edit its notes file in a pull request. When it merges, the GitHub release's text updates to match. The tag and files never change. (#22)

## ⛓️‍💥 Breaking Changes

### The tag points at the commit you reviewed

Release Planner now tags the commit your release pull request branched from, the one its checks and builds ran on, instead of the merge commit. Squash and rebase merges work the same way. If a script expects the tag on a merge commit, update it. (#22)

### A release pull request may change only release notes

Validation now fails a release pull request that changes anything besides release notes files. Merge other changes in their own pull request first. (#22)

### The Release workflow changed

The generated Release workflow has new jobs and a new retry input, and some commands used only by the workflow changed. Until you rerun `install`, `release-planner check` fails, and a manual retry needs the new input:

- A manual retry now takes `merged-commit`, the full SHA of the commit the release pull request merged as, instead of the base and head SHAs.
- `validate --event` and `publish --commit` are removed.

If a branch ruleset requires one of the Release workflow's checks, confirm its name still matches. (#22)

### Upgrade steps

1. Install v0.4.0:

   ```sh
   curl -fsSL https://raw.githubusercontent.com/fabricahq/release-planner/v0.4.0/install.sh | sh -s -- --version v0.4.0
   ```

2. Set `version: v0.4.0` in `.release-planner/config.yml`.
3. Run `release-planner install`, and commit the updated files in one pull request.
4. Update any script or runbook that retries a release with the base and head SHAs to use `merged-commit`, or that expects the tag on the merge commit.
